# Progressive Delivery — Phase 1 Plan

_Status: design settled, nothing built. Last updated 2026-09-17._
_Verified against `workflows@594548f`, `StateOps@95feb8ab6` (Rollouts + notifications
files re-checked against `origin/main` 2026-09-17), `helm-charts` local checkout,
`nexus@7286753`, and **Argo Rollouts v1.8.3** — the installed version (argo-helm chart
`2.39.6`). The readthedocs `stable` docs describe v1.10.0; every claim below was
checked against the v1.8.3 source where the two could differ._

## 1. Goal

Make the GitHub Actions promotion pipeline aware of whether a deployment actually
succeeded in ArgoCD / Argo Rollouts before the next ring can proceed. Keep the
existing human approval between rings, but make it impossible for that approval to
take effect until the current environment's deployment is confirmed healthy. On
failure: block promotion and surface it (GitHub status + message).

## 2. Hard constraints (from the team)

1. **No self-hosted GitHub runners (ARC) in staging or production.** ARC exists in
   dev / dev-ci only. Any design needing a runner inside a stg/prod cluster is out.
2. **ArgoCD is not internet-reachable** (verified, see 3.3). A GitHub-hosted runner
   cannot poll it. The signal must originate inside the cluster and travel outward.
3. A cluster-side component holding **scoped GitHub write credentials is acceptable**.
4. **Human approval between rings stays.**
5. Rings will be **split into finer units**, but all clusters within a phase must
   succeed before promotion.
6. Phase 2 is progressive delivery with traffic shifting; do not block it.

## 3. Verified architecture facts

### 3.1 The pipeline today (`frontegg/workflows`)

- `main.yaml` -> `main-with-image.yaml`. Job chain:
  `params -> build-and-publish-docker -> deploy-to-staging -> deploy-to-australia
  (also deploys production-uk) -> deploy-to-us -> deploy-to-global`.
- Each production ring has a GitHub `environment:`; **required reviewers are
  configured in GitHub**, so a human already gates every ring. The approval prompt
  appears only once the job's `needs:` are satisfied.
- Gates per ring: Split.io `allow-deployments` (all rings), Checkly against the
  *previous* ring (AU/US/global), k6 stress (AU only).
- The deploy step is `shared-actions/tag-versions`, which writes `appVersion` +
  `workflowRunId` to AppState and pushes git tags to the service repo:
  `<env>-<YYYYMMDD.HHMMSS>-<sha>`, force-moved `<env>`, `venv-latest` (staging).
- **The job goes green when the AppState commit lands.** Nothing observes the rollout.
  Consequence today: AU's Checkly checks can run against staging before staging has
  finished rolling out.
- Pre-existing traps: `deploy_au: false` skips AU so `needs.deploy-to-australia.result`
  is `skipped` not `success`, blocking US and global; UK has no opt-out (hardcoded
  inside the AU job); stress-test verification steps are unreachable (no
  `continue-on-error`, guards default to `success()`); `code_changed` input is
  required but unused; hybrid path is `if: false`.

### 3.2 The wire (`frontegg/AppState`)

- `applications/<repoName>/<unifiedTag>/values.yaml` containing `appVersion`,
  `workflowRunId`. Env dirs: `staging`, `production-au`, `production-uk`,
  `production-us`, `production-global`.
- Read by ArgoCD at **`HEAD`**, not per-env branches. Isolation is by path only.

### 3.3 GitOps side (`frontegg/StateOps`, local `~/frontegg/development/ops/StateOps`)

- unifiedTag fan-out: `staging` -> staging-group; `production-au` -> prd-ca-c1,
  prd-ap-se2; `production-uk` -> prd-eu-w2; `production-us` -> prd-us-e1, prd-us-e2;
  `production-global` -> prd-eu-w1, prd-eu-n1. **The AU job today hits 3 regions in
  3 AWS accounts.**
- Service Applications are generated by
  `cluster-applications/main/cluster-applications/templates/argo-app-v2.yaml` from
  `unifiedApps.apps`, gated by exact-name match on `global.supportedServices`.
  Production lists only `-v2`/new names, so the legacy `charts` path (45 entries,
  ArgoCD Image Updater) renders nothing in prod. **No Image Updater on the live path.**
- Each v2 Application is **multi-source**, in this order (index matters — see 6.4):
  `[0]` Helm chart `unified-chart-<unifiedTag>` from `frontegg.github.io/helm-charts`;
  `[1]` `git@github.com:frontegg/<repoName>.git` at `targetRevision: <unifiedTag>`
  (ref `values`); `[2]` `git@github.com:frontegg/AppState.git` at `HEAD` (ref `appstate`).
- Value-file stack (last wins): `$values/k8s/default.values.yaml`,
  `$values/k8s/<unifiedTag>.values.yaml`, `$values/k8s/<envID>.values.yaml`,
  `$appstate/prod/default.yaml` (when `global.prod`),
  `$appstate/applications/<repoName>/<unifiedTag>/values.yaml`,
  `.../override.yaml`. `appVersion` is therefore an ordinary Helm value.
- Sync policy: automated + prune + selfHeal + allowEmpty; retry 10x 5s->3m.
- **ArgoCD ingress is internal everywhere**: workload clusters
  `environment-infrastructure-charts/argo-release/values.yaml:93`
  `alb.ingress.kubernetes.io/scheme: internal`; management cluster
  `management-clusters/jarvis/argocd/argo-cd-internal-ingress.yaml` is also
  `scheme: internal` with `inbound-cidrs` limited to private ranges + one /32.
- **ArgoCD Notifications controller is already enabled in all 10 environments**:
  `environments-values/common/notifications.values.yaml` (`notifications.enabled: true`)
  plus one `<env>.notifications.values.yaml` per environment. Existing triggers:
  `on-deployed`, `on-health-degraded`, `on-sync-failed`, `on-sync-running`,
  `on-sync-status-unknown`, `on-sync-succeeded`, `progressing`, `healthy`. Services:
  `slack`, `opsgenie`. Adding `service.github` is a values change to a file that
  already exists — not a new component.
- **Argo Rollouts v1.8.3 installed in all 10 envs** (`namespaces/argo-rollouts/frontegg-argo-rollouts`,
  argo-helm chart `2.39.6`, unchanged since 2025-06-18, wave 600, per-env values in
  every `environments-values/*/main/`). The unified-chart Rollout template sets neither
  `progressDeadlineSeconds` nor `progressDeadlineAbort`, so the defaults apply: 600s,
  **no abort on deadline** (see 5.3).
- **The Gateway API traffic-router plugin is configured in `staging-group` only**,
  pinned to `argoproj-labs/gatewayAPI` **v0.2.0** (released 2024-02-26; latest is
  v0.17.0, 2026-09-01). No production `frontegg-argo-rollouts/values.yaml` declares
  `trafficRouterPlugins`, so canary mode cannot be switched on in production without a
  StateOps change.

### 3.4 The service chart (`helm-charts/common/unified-chart`)

- Renders **three Rollouts per service**: `web`, `high-priority`, `worker`
  (`templates/{web,high-priority,worker}/*-rollout.yaml`), each with HPA + KEDA
  ScaledObject. **All services are already Rollouts.**
- Strategy is canary when `argoRollouts.progressiveDelivery.enabled` (default
  `false`), else `blueGreen` with `autoPromotionEnabled: true` hardcoded (the upstream
  default anyway).
- Canary steps: `setCanaryScale(1)` -> `setHeaderRoute` (match
  `frontegg-trace-id` prefix `automation`) -> `analysis` -> remove header route.
  **No `pause` step.** Traffic routing via `argoproj-labs/gatewayAPI` plugin
  (`useHeaderRoutes: true`, canary/stable Services, header route pre-declared in
  `managedRoutes` as the plugin docs require). **The plugin binary is deployed in
  staging only** (3.3).
- Analysis (`*-analysis-template.yaml`): one `web` provider metric — POST to
  `blackBox.url` (default `nexus-v2-web.frontegg.svc.cluster.local/blackbox`),
  `successCondition: result.status_code == 200`, `count: 1`, `failureLimit: 1`,
  `consecutiveErrorLimit: 0`, `timeoutSeconds: 1200`.
- **That analysis can only fail through the Error path** (v1.8.3
  `analysis/analysis.go`, `assessMetricFailureInconclusiveOrError`): a metric is Failed
  only when `failed > failureLimit`, so with one measurement and `failureLimit: 1` a
  failed check still ends **Successful**. What aborts the Rollout is a non-2xx response
  — the web provider marks it Error and `consecutiveErrorLimit: 0` fails the run. nexus
  `/blackbox` (`internal/handler/handler.go`) dispatches a GitHub Actions blackbox
  workflow, waits for its conclusion, answers **500** on failure and `{"status": true}`
  with 200 on success. `result.status_code` therefore names a field that never exists
  and the `successCondition` is dead code. It works by accident (see 8.8, 10.4).
- Consequence: **Application health converges on its own** (no manual pause in
  either mode) and a full canary is bounded at roughly one 20-minute call plus
  rollout time. Analysis, experiment and pause steps do not count toward
  `progressDeadlineSeconds` (`rollout/sync.go` `isIndefiniteStep`), so the 20-minute
  wait cannot time the Rollout out. A 45–60 minute job timeout is comfortable; the
  6-hour cap is far.

### 3.5 GitHub

- Org `frontegg` is on **GitHub Enterprise** (`gh api /orgs/frontegg` -> `plan: enterprise`).
  Custom deployment protection rules are available (public preview).

## 4. Decision log

| # | Decision | Rationale |
|---|---|---|
| 1 | **Success signal = ArgoCD Application health** (Synced + Healthy) | One signal per service per cluster; Application health is the worst child, so it is Healthy only when all three Rollouts are fully promoted. Terminates on its own (3.4). |
| 2 | **Gate = the previous ring's job waits** (polls GitHub) | Zero new components; reuses `needs:`. Next ring's approval prompt cannot appear until the current ring is confirmed healthy — the most literal match to the requirement. |
| 3 | **ArgoCD writes both a commit status and a GitHub Deployment status** | Commit statuses: one API call to read while polling. Deployments: Environments-tab view, fresh record per run, and the form a protection rule would read later. |
| 4 | **Statuses attach to the service-repo commit** (multi-source `revisions[1]`) | The commit the developer pushed; per-service so no monorepo noise; `tag-versions` already force-moves the `<env>` tag to it. AppState is a shared monorepo at `HEAD` — statuses there land on descendants when pushes coalesce. |
| 5 | **Human approval stays** | Required. Automated gate composes with it, does not replace it. |
| 6 | **Cluster-side GitHub App with scoped creds is acceptable** | Deployments: write + Commit statuses: write, nothing else. PEM via ESO, never inline. |
| 7 | **Kargo — parked** (implicit; not explicitly confirmed) | Its entire GitHub integration is Akuity-Enterprise-only (see 5.1). |
| 8 | **GitOps Promoter — spike, not adopt** | Coherent as long-term engine (see Option C) but has an unverified multi-source blocker. |
| 9 | **Custom protection rule — phase-2 upgrade path** (Option B) | Drop-in replacement for the waiting job if idle runners or the 6-hour cap bite. |

Corrections made during design (recorded so they are not re-made): services *are*
Rollouts already (not Deployments); rings *are* human-gated today (not auto-flowing);
progressive delivery machinery (Gateway API routing, AnalysisTemplates) *already
exists* behind a feature flag — in the chart; the traffic-router plugin itself is
deployed in staging only (3.3).

### 5.2 ArgoCD Notifications facts that shape the implementation

- Stock GitHub template defaults `repoURLPath`/`revisionPath` to `spec.source.repoURL`
  and `syncResult.revision` — **both empty on multi-source apps**
  ([argo-cd#15617](https://github.com/argoproj/argo-cd/issues/15617), open since 2023).
  Must set both explicitly with indexed access:
  `{{(index .app.spec.sources 1).repoURL}}` /
  `{{index .app.status.operationState.syncResult.revisions 1}}`.
- Stock `on-deployed` trigger uses `oncePer: syncResult?.revision`, which is `""`
  on multi-source, so it **fires once and never again**. Do not copy it.
- **With `oncePer`, a failed send is recorded as sent and never retried**
  ([argo-cd#20879](https://github.com/argoproj/argo-cd/issues/20879), closed not-planned).
  Mitigation: a paired trigger *without* `oncePer` (that path does retry) + a hard CI timeout.
- Failure templates should use `status.sync.revisions[i]`, not `syncResult`, which
  can be nil when a sync fails before producing a result
  ([argo-cd#29575](https://github.com/argoproj/argo-cd/issues/29575)).
- Argo Rollouts notifications have **no `oncePer` and no retry** — verified in v1.8.3
  `utils/record/record.go`: the event recorder calls `RunTrigger` then `Send` directly,
  logs a failed send and moves on, and never reads or writes the
  `notified.notifications.argoproj.io` state annotation
  ([argo-rollouts#5037](https://github.com/argoproj/argo-rollouts/issues/5037), open,
  external reporter). The docs page lists nine triggers (`on-rollout-completed`,
  `on-rollout-aborted`, `on-analysis-run-failed`, `on-analysis-run-error`, ...) and
  says nothing about either. Use them only for fast-fail detail, not as the gate.
- Multi-source revision arrays (`status.sync.revisions[]`,
  `status.operationState.syncResult.revisions[]`) are indexed like `spec.sources`;
  populated for multi-source since after ArgoCD 2.6.7 — **verify on the deployed version**.
- ArgoCD polls git every ~3 min by default (no inbound webhook path exists) — adds
  up to 3 min latency per ring.
- Rate limits are per GitHub App installation, shared across all clusters using it.

### 5.3 Health semantics

- `Deployment` Healthy = observedGeneration caught up, replicas updated and available.
  Never inspects restarts or CrashLoopBackOff; a crashlooping new version sits in
  `Progressing` until `progressDeadlineSeconds` (default 600s) then `Degraded`.
- `Rollout` health: ArgoCD's `health.lua` surfaces `status.phase` as-is, mapping
  `Paused` -> `Suspended`; the phase is computed in v1.8.3
  `utils/rollout/rolloututil.go`. **Healthy** = `stableRS == currentPodHash` (fully
  promoted) and `available >= updated >= desired`. **Degraded** = `InvalidSpec`,
  `RolloutAborted` or `ProgressDeadlineExceeded`. AnalysisRun failure or error aborts
  the Rollout -> `Degraded`; the stable ReplicaSet keeps serving.
- **Degraded is not always terminal.** With `progressDeadlineAbort` unset (default
  `false`), a Rollout that shows no progress for `progressDeadlineSeconds` (600s) is
  marked `Degraded` with reason `ProgressDeadlineExceeded` **but keeps rolling**, and
  flips back to Progressing then Healthy once pods come up. StateOps hit exactly this
  in 2024 (PR #772). Only `RolloutAborted` stays until someone retries. See 8.9.
- Application health = worst child, including non-Rollout children (ExternalSecret,
  ScaledObject, hook Jobs). **Any child stuck in `Progressing` means the app never
  reaches Healthy** — see 8.1.

### 5.4 GitHub facts

- Job hard cap 6h; workflow 35d; environment approvals wait up to 30d **unbilled**.
- `GITHUB_TOKEN`-created events do not trigger workflows (except `workflow_dispatch`,
  `repository_dispatch`). Statuses written by a GitHub App *do* trigger `deployment_status`.
- Deployment API: create with `auto_merge: false`, `required_contexts: []` (otherwise
  409s on refs behind default branch / pending contexts). notifications-engine defaults
  `AutoMerge` to true when it creates a Deployment itself — pre-create from the pipeline.
- Custom protection rules: GitHub `POST`s `deployment_protection_rule` to a URL you
  configure when a job reaches the environment; approve via
  `POST /repos/{o}/{r}/actions/runs/{run_id}/deployment_protection_rule`
  (`environment_name`, `state: approved|rejected`, `comment`). **"GitHub Apps can only
  review their own custom deployment protection rules."** Public preview.
- App permissions: Deployments: write (deployments + statuses); Commit statuses:
  write; Checks: write only if check runs are wanted. Avoid Contents/Actions write.
- Hosted Linux runner listed at $0.006/min (unverified against invoice); a 20-min
  wait ≈ $0.12.

## 6. Implementation options

### Option A — Previous ring's job waits (chosen for phase 1)

**Flow per ring (e.g. AU):**
1. Job resolves the ring's expected cluster set (see 8.5).
2. Pre-writes `pending` commit status on the service SHA for each context
   `argocd/<cluster>/<service>` and creates one GitHub Deployment per cluster
   (`ref: <sha>`, `environment: <cluster>`, `auto_merge: false`,
   `required_contexts: []`, payload `{ring, run_id, service}`). **This resets stale
   statuses** — see 8.2.
3. Runs the existing gates and `tag-versions`.
4. If `appVersion` did not change, **skip the wait** (no sync will occur, no status
   will be posted).
5. Polls `GET /repos/{o}/{r}/commits/{sha}/status` (combined) every 15–60s with
   backoff; success when every expected context is `success`; fail fast on any
   `failure`/`error`; `timeout-minutes` 45–60 on the job.
6. On failure/timeout: mark Deployments `error`/`failure`, write
   `$GITHUB_STEP_SUMMARY` table of per-cluster states, Slack via existing
   `rtCamp/action-slack-notify`, fail the job. `needs:` then blocks downstream rings.

**StateOps changes** (`environments-values/common/notifications.values.yaml` + per-env):
- `service.github`: `appID`, `installationID`, `privateKey: $github-privateKey`
  (secret item supplied via ESO / ClusterSecretStore — **not inline**).
- `context`: per-cluster identity (`cluster: prd-us-e1`) in each env's notifications
  values file.
- Triggers: `on-appstate-deployed` (when Synced && Healthy && phase Succeeded &&
  `syncResult.revisions[1] == sync.revisions[1]`, `oncePer: syncResult.revisions[1]`),
  a paired `-retry` variant with no `oncePer`, `on-appstate-degraded`
  (`oncePer: sync.revisions[1]`), `on-appstate-sync-failed`.
- Templates: explicit `repoURLPath: {{(index .app.spec.sources 1).repoURL}}`,
  `revisionPath: {{index .app.status.operationState.syncResult.revisions 1}}`
  (success) / `{{index .app.status.sync.revisions 1}}` (failure); `status.label:
  argocd/{{.context.cluster}}/{{.app.metadata.name}}`; `deployment.environment:
  {{.context.cluster}}`, `autoMerge: false`, `requiredContexts: []`.
- A test asserting `unifiedApps.common.sources[1]` is the service repo (see 8.4).

**workflows changes** (`main-with-image.yaml`):
- Steps 1, 2, 4, 5, 6 above in each deploy job (~40 lines via `actions/github-script`).
- Ring -> cluster map as a repo variable or input (see 8.5).

**GitHub:** one org App (e.g. `frontegg-argocd-reporter`), Deployments: RW +
Commit statuses: RW, webhook deactivated, installed on service repos only. PEM in
AWS Secrets Manager -> ESO -> `argocd-notifications-secret` in each cluster.

### Option B — Custom protection rule + thin approver (phase-2 upgrade)

Same ArgoCD side as A. Each production environment gets a custom protection rule
alongside required reviewers. Receiver: Lambda + API Gateway. On
`deployment_protection_rule` webhook: store `{run_id, environment, sha}`; on an
EventBridge schedule re-check the previous ring's statuses on that sha; all green ->
`approved`; any red -> `rejected` with a comment naming the cluster. Same GitHub App
as ArgoCD. No idle runner, 30-day ceiling, both gates must pass. Adds state (DynamoDB).

### Option C — GitOps Promoter as promotion engine (spike first)

AppState restructured to **branch-per-environment**; CI writes to `<env>-next`;
Promoter opens/merges PRs; `ArgoCDCommitStatus` gates on previous-ring health; the
merge into an env branch is a push that triggers a workflow running Checkly/k6/Split,
which writes a commit status Promoter consumes as a `proposedCommitStatus`; human
approval = PR review. Replaces the ring logic in `main-with-image.yaml`.

**Blocking unknown:** `ArgoCDCommitStatus` reads `spec.source.targetRevision`
(single-source). If it does not understand `spec.sources`, it cannot see these
Applications. **Spike:** install Promoter in dev, point one `ArgoCDCommitStatus` at a
multi-source Application, see whether a CommitStatus is produced. Also unverified:
whether Promoter accepts CI (not the hydrator) as the writer of `-next` branches.

### Comparison

| | A | B | C |
|---|---|---|---|
| New things to run | 0 | Lambda + table | Promoter + AppState restructure |
| Idle runner while waiting | yes | no | no |
| Wait ceiling | 6h | 30d | n/a |
| Touches service repos | no | no | yes |
| Replaces ring logic | no | no | yes |
| Blocking unknown | none | none | multi-source support |
| Effort | days | 1–2 weeks | a quarter |

- [ ] The argo-helm chart in `argo-release` installs the notifications controller

- [ ] Trigger expressions with `revisions[1]` work via

- [ ] Confirm the AnalysisTemplate reading (3.4) with a `dryRun` metric in staging: a

## 8. Review findings (Fable, 2026-09-16; items 8–11 added 2026-09-17 after checking the Argo Rollouts docs and v1.8.3 source)

1. **Stale success on rollback** — commit statuses persist; rolling back to a commit
   that was deployed before finds its old `success` and passes instantly. **Fix:
   pre-write `pending` on every expected context before touching AppState** (A step 2).
   Deployments avoid this by being fresh per run.
2. **Lost notification = infinite wait** — see 5.2 `oncePer`. Paired no-`oncePer`
   trigger + hard job timeout + mark Deployment `error` on timeout.
3. **Unverified: apps reach `Healthy` today** — checklist 7 item 1.
4. **Positional source index is fragile** — `revisions[1]` relies on
   `unifiedApps.common.sources` order `[chart, service repo, AppState]`. Add a test in
   StateOps or use expr `findIndex`.
5. **Ring -> cluster map in two places** — StateOps' unifiedTag fan-out vs the
   job's expected-context set. Drift = ungated cluster or permanent hang. Decide the
   single source of truth now, especially since rings are being split.
6. **Rollback semantics** — "failed" means stopped and alerted, not reverted.
   Rollouts abort to stable on analysis failure; a `Degraded` Deployment stays so.
7. **Positive side effect** — AU's Checkly checks will run against a staging that has
   actually finished rolling out.
8. **The unified-chart analysis cannot fail on a measurement** — `failureLimit: 1`
   with `count: 1`; only a non-2xx from nexus aborts (3.4). Harmless for phase 1,
   whose gate is Application health and where a 500 does abort, but fix it before
   phase 2 leans on analysis: `failureLimit: 0` and a `successCondition` that matches
   the real body, or no condition at all.
9. **`Degraded` can be transient** — `ProgressDeadlineExceeded` without
   `progressDeadlineAbort` recovers on its own (5.3). If Option A's degraded trigger
   writes `failure` and the job fails fast on it, a slow but successful rollout (image
   pull, node scale-up) fails the ring. Either set `progressDeadlineAbort: true` in the
   chart so that Degraded always means aborted, or have the poller treat `failure` as
   "keep waiting, flag it in the summary" and let only the timeout end the job.
   Decide in 9.
10. **Canary mode is staging-only today** — the Gateway API plugin is not configured in
    any production environment and is fifteen releases behind (3.3). Not a phase-1
    blocker, since blue-green converges the same way, but a phase-2 prerequisite.
11. **nexus is a live precedent for in-cluster -> GitHub** — it holds a GitHub token
    through an ExternalSecret and dispatches and polls GitHub Actions from inside
    staging and five production clusters (prd-ap-se2, prd-ca-c1, prd-eu-w1, prd-eu-w2,
    prd-us-e1). It could even post the commit status itself. Not chosen: it is absent
    from prd-eu-n1 and prd-us-e2, and it would couple the gate to a service deploy.
